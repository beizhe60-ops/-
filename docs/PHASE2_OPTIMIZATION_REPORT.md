# PHASE 2 前端性能与请求反馈

2026-09-22。本轮只修改 static/console.js，新增可复跑浏览器回归测试和报告。没有部署或修改后端、数据库、Telegram 连接、队列、权重算法与业务规则。保留此前所有未提交改动。

## 修改内容

- 概览保存上次实际渲染的 HTML，生成内容完全相同时跳过 innerHTML 和事件重新绑定。只缓存一份当前概览，不缓存服务器配置。指标或绑定内容变化仍会更新。
- 后台更新发生实际重绘时，恢复任务按钮或内容链接的焦点及窗口滚动位置。轮询请求返回后再次检查弹窗和页面可见状态，避免请求发出后打开弹窗造成其原按钮被替换。
- 消息记录的筛选、上一页、下一页、刷新统一通过带错误处理的入口。请求中保留旧列表，显示“加载中…”，设置 aria-busy 并禁用相关控件；重复触发不会重复发送该记录请求。
- 页码和已应用筛选仅在成功取得记录后提交。失败显示原因，保留旧列表、筛选输入和原页码，按钮恢复可用。成功显示“记录已更新”，覆盖之前的失败提示。
- 服务启动/暂停按钮的 pending 状态独立保存，后台状态刷新不能提前重新启用它；成功提示使用点击时的操作意图，避免轮询改变状态后提示相反结果。

## Before / After

|场景|Before|After|
|---|---|---|
|内容不变的概览，31 秒|初始渲染外，额外重建 2 次|额外重建 0 次|
|相同 31 秒内状态 API|3 次（包含初始化）|3 次，刷新间隔不变|
|筛选接口返回 500|未处理 Promise 异常|明确错误提示，保留输入和旧列表，可重试|
|翻页失败|请求前已推进 offset，重试可能继续跳页|失败不推进 offset；下一次重试仍取正确页|
|慢记录请求重复点击|没有统一 pending 防护|相关控件禁用，同一时刻只执行一个记录操作|
|服务请求中收到轮询|serviceHeader 无条件恢复按钮|直到服务操作结束才恢复|

概览仍会生成并比较 HTML；本轮未改成虚拟 DOM 或逐行差分渲染。内容真正变化时仍重建内容区。本次降低的是无变化的 DOM 重建成本，不声称减少 API/SQL 或提高 Telegram 发送吞吐。

## 验证

- 全套 Python 回归：63 passed，705 条已有弃用类警告。
- node --check、git diff --check 通过。
- 浏览器自动化：Chrome 桌面 1440×1000 与手机尺寸模拟 390×844，各覆盖内容不变、指标变化、焦点和滚动、请求途中打开弹窗、关键词/来源群/目标群草稿保存、私信文案和权重编辑保存、服务 pending、分页成功与失败重试、筛选失败保留输入、重复点击、刷新失败及恢复。全部通过，无 pageerror，无页面横向溢出。
- 新测试在本轮修改前的 JS 上执行，首先因无变化刷新仍替换节点而失败；在修改后通过。
- 真实本地 FastAPI + 临时 SQLite + 虚构账号复测 31 秒：状态请求 3 次、额外内容替换 0 次、>50ms 长任务 0、脚本错误 0。另一账号页弹窗保持打开，新增状态请求 0，关键词草稿保持。
- 浏览器 API 故障注入和保存操作使用虚构响应；本地后端测试没有启动 Telegram worker，没有向真实用户发送消息。手机测试是浏览器尺寸/触摸模拟，不等同于真实手机性能。

证据：performance-baseline/phase2-browser.json、phase2-live.json。PHASE 0 的 browser.json 仍保留作为旧基线。

## 复跑

从 telegram-ops 目录运行：

```sh
PLAYWRIGHT_MODULE=/path/to/installed/playwright node tests/browser/phase2.cjs
```

使用已有 Playwright 和 Chrome。测试自行启动仅监听本机的临时静态服务并模拟全部 API，不需要真实账号。没有增加项目依赖或升级版本。
