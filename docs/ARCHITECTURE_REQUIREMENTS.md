## 2. 产品目的与范围

提供中文网页后台，在 Linux 服务器持续运行 Telegram 消息监测、筛选、定向转发与私信分配。用户通过网页完成配置，不需要保持浏览器打开，也不需要在服务器安装 Telegram 桌面客户端。

核心流程：

```text
监测账号 A
  → 绑定的监测群组 ID
  → 发言与实际发言者识别
  → 关键词过滤
  → 绑定的转发目标群组 ID
  → 绑定该接收群组 ID 的私信账号池
  → 按权重分配给一个 B 账号
  → 使用文案向目标用户私信
```

监测转发可以在没有私信账号的情况下独立运行。私信账号配置接收群组和文案，不需要在每条新监测绑定中指定固定 B。

网站包括：运行概览、账号管理、任务与过滤、消息记录、不再联系、系统设置。新服务与已有记账、转发机器人独立部署和存储，不能破坏其运行。

不属于当前已确认范围：自动加群、历史消息批量采集、AI 客户判断、绕过平台限制、多租户、多服务器分布式执行、任意成员消息触发私信。是否扩展需另行明确。

## 3. 名词与配置对象

| 对象 | 含义与边界 |
|---|---|
| 监测账号 A | 登录 Telegram 用户账号，负责读取来源群并向目标群发送标准消息 |
| 私信账号 B | 独立登录的 Telegram 用户账号，接收绑定群消息并执行被分配的私信 |
| 监测群组 ID | A 明确配置的来源群标识 |
| 转发目标群组 ID | 一条监测绑定的输出目标；也是 B 可绑定的接收群 ID |
| 监测绑定 | 监测账号、一个或多个来源群 ID、可暂未配置的目标群 ID、过滤条件与启停状态 |
| 私信接收绑定 | 私信账号、一个或多个接收群 ID及文案配置 |
| 账号池 | 对某个接收群显式绑定且满足运行条件的私信账号集合 |
| 发送任务 | 持久化的单条转发或私信工作，记录来源、分配账号、配置依据和执行结果 |
| 群名称 | 展示辅助信息，不能用于路由选择、授权或轮询入池判断 |

同一个物理群可以同时作为 A 的转发目标和 B 的接收群。群 ID 相同才表示同一个目标，名称相同不代表同一个群。

## 4. 已确认产品需求

### 4.1 网页与账号登录

- 账号管理分为监测账号、私信账号两个入口，登录与状态分别管理。
- Telegram 登录表单只包含手机号、验证码、二级登录密码；未启用两步验证时允许密码留空。
- API ID / API Hash 在系统设置统一配置，账号登录不重复填写应用凭据。
- 显示账号是否已登录、连接情况、异常原因及发送开关；支持重新登录和退出账号。
- 后台登录与 Telegram 账号登录是两套独立认证，不能混淆。

### 4.2 监测与定向转发

- 所有功能群组直接通过完整群组 ID 绑定，不以同步群列表作为保存绑定的前提。
- 在监测账号下配置“监测来源群 ID → 转发目标群 ID”，并能查看、编辑和启停该绑定。
- 一条绑定支持多个来源群和一个转发目标。需要不同目标时建立不同绑定。
- 转发目标群组 ID 可以暂时留空保存，以 NULL 表示未配置，不使用示例 ID 或占位群。未配置时显示“待配置”，保持暂停且不能启用；补填有效 ID 后可手动启用。清空已有目标按修改绑定规则暂停并取消旧待发送消息。
- 仅处理绑定来源群内符合规则的新发言，不因账号还加入了其他群而扩大监测范围。
- 根据配置的关键词筛选目标发言；网页可以配置过滤条件并模拟验证。
- 转发目标支持私有群和公开群，统一使用完整数字群 ID，不依赖公开用户名或邀请链接，不要求将私有群公开。
- 账号需要能读取来源群、在目标群发言；填写 ID 不等于已经加入群或已经验证权限。
- 监测转发不依赖 B 登录、接收绑定或私信文案。

### 4.3 固定消息格式与身份

转发内容统一为：

```text
群组-该用户发言的内容-@用户名
```

- 末尾用户名取自实际发言者，不从正文其他 `@提及` 中猜测。
- 原群名称、原始内容和实际发言者信息应有可追溯记录；群名称不承担路由作用。
- 接收侧不能因为正文含有其他用户名而改变收件人。

### 4.4 私信接收与文案

- 私信账号单独绑定接收群 ID，绑定与监测账号的转发目标通过 ID 对接。
- 网页设置私信文案；支持插入目标用户名。
- 识别符合处理规则的消息后自动生成私信任务，关闭网页不影响后台执行。
- 未绑定接收群的账号不得处理该群消息，也不得因同步过该群而进入轮询。

### 4.5 权重轮询

- 每个私信账号可设置轮询权重，数字越大，获得的新任务份额越高。
- 同一接收群的有效账号之间按权重分配，单条消息只分配一次。
- 例如在账号集合与可用状态稳定时，权重 3 与 1 的分配比例应趋近 3∶1；不表示保证每个短时间窗口都严格等比例。
- 权重修改作用于后续分配；已分配消息不因调整权重而换号。

### 4.6 持续运行与共存

- 服务部署在 Linux，具有独立目录、运行身份、依赖环境、数据库和端口。
- 开机启动与异常恢复可管理，保留必要日志和数据备份。
- 网页关闭不停止业务；重启后的连接、队列和运行状态应有明确恢复策略。
- 不能覆盖、停止或混用现有记账与转发机器人的程序、数据库和凭据。

## 5. 当前业务规则基线

以下规则用于维持重构前后的行为一致性。需要调整时，更新本文件和相关验收场景。

### 5.1 ID、过滤与内容

- 群 ID 使用完整负整数；当前接口范围为 `[-2^52, -1]`，拒绝正数、零、布尔值、小数、群名称及邀请链接。网页将严格校验后的文本转换成整数再提交。
- 多个 ID 可以逐行或逗号输入，保存时去重；当前每组最多 200 个。
- 同一监测绑定的来源群不能包含其转发目标群。
- 当前关键词支持任意命中、全部命中、整条发言精确匹配；关键词必填，另有排除词与忽略用户。
- 包含关键词与排除关键词以空白（空格、连续空格、换行、制表符、全角空格）分隔，也兼容中英文逗号。例如“携程 卡密 大润发 盒马”为四个词。模拟测试与实际过滤使用同一解析规则；含空格的原有短语也将拆为多个词，精确匹配针对拆分后的单个词。忽略用户的解析规则保持不变。
- 无有效用户名、机器人、系统自身账号或不符合条件的消息跳过；自身发出的来源消息不触发监测转发。
- 转发按纯文本发送，换行折叠为空格；超出平台长度限制不截断后冒险发送，应留下可理解的处理结果。
- 模拟测试不得调用真实发送接口。

### 5.2 私信边界与去重

- 当前 B 只处理已绑定群中、本系统对应监测账号发送的标准消息，不处理任意群成员的用户名提及。
- 私信接收当前仍依赖相应监测任务及其启用状态。这是待拆分的实现耦合，不应被误描述为已完全独立的接收引擎。
- 新任务使用分配账号的私信文案；旧任务若保留独立文案，则旧任务文案优先。需要统一其最终归属，见第 10 节。
- 私信实际发送前解析用户名对应用户 ID；如与原记录身份不一致，停止发送并记录原因。
- 按 Telegram 用户 ID 跨任务去重；检查不再联系名单、忽略用户、机器人和不可联系对象。
- 当前去重默认不自动过期。是否允许再次联系、按什么时间窗重置尚未确认。

### 5.3 轮询与执行状态

- 当前权重为 1–1000 的整数，默认 1，采用持久化的平滑加权轮询。
- 入池条件包括显式接收绑定、私信角色、账号可用且在线、允许发送与私信、未处于平台等待期。
- 多个 B 收到同一群消息不能推进多次有效分配；保存分配结果与轮询进度应处于一致事务中。
- 当前所有候选均不可用时，将已接收的事件保留给接收该事件的 B 等待，不盲目换号重发。所有 B 离线期间的消息不保证补齐。
- 转发和私信均持久化排队，状态包括待发送、等待、发送中、已发送、失败、结果不确定、跳过及取消。
- Telegram 等待限制按返回时间处理；失败不无限重试。
- 2026-09-23 运行时优化：最多同时执行 4 个账号发送批次；同一账号串行，每批最多处理 10 条已到期任务，按任务 ID 顺序执行。账号间轮换调度，离线账号的积压不占用在线账号的候选名额。主循环不等待网络发送完成。
- 发送失败或结果不确定时结束该账号当前批次，让出并发名额；剩余待发送任务仍属于原账号，由后续调度处理。失败/结果不确定任务不会因此重新入队。
- 账号初始化也最多并行 4 路，使用与发送、登录、同步一致的账号操作锁。配置修改不持有覆盖 Telegram 网络等待的全局锁。
- 初始化/群同步网络阶段采用 20 秒超时，用户名解析和单次发送采用 60 秒超时，断开连接采用 10 秒超时。已进入发送阶段后超时记为结果不确定，不自动重发；断开超时留下日志。超时依赖异步客户端响应取消，不承诺底层网络资源在硬截止时间内全部释放。
- 外部发送成功与本地结果提交不可能天然构成同一事务。进程在发送过程中中断时，保留结果不确定状态，不自动重发。

### 5.4 修改配置与恢复

- 新监测绑定默认暂停；修改绑定后暂停，并取消该任务旧的待发送消息，核对后再启用。
- 私信解绑取消该账号在移除群中的待发送消息；修改文案取消该账号旧待发送私信。
- 已发出或正在执行的网络请求可能已经交付，界面不能宣称一定撤回成功。
- 业务运行状态持久化。服务重启不自动扫描历史消息，也不承诺补齐停机期间消息。
- 暂停时取消并等待受管理的发送、初始化及主循环任务，再断开客户端；停止后迟到的事件不能再新增任务。发送前检查绑定、权限和任务状态；用户名解析期间发生配置变更时也须重新检查，不能先占用用户去重记录再发现任务已失效。
- 旧配置迁移保留明确的来源与目标 ID，仅把原任务明确指定的 B 接收群迁移为绑定，不因同步群名称而自动授予接收范围。
- 已有接收绑定，包括用户主动清空的绑定，不能在再次迁移时被覆盖或恢复。
- 系统应用凭据更新目前只用于后续新增账号，既有账号保留原凭据；不能无提示地替换已有会话的连接参数。

## 6. 架构目标

### 6.1 模块职责

| 层次 | 目标职责 |
|---|---|
| 网页 | 页面组件、表单状态、可理解的反馈；不实现最终路由和授权判断 |
| 接口 | 后台认证、严格输入校验、配置读写和状态查询 |
| 业务服务 | 监测规则、接收规则、身份判断、去重与配置变更语义 |
| Telegram 适配 | 登录、连接、实体解析、事件转换、发送与平台错误归一化 |
| 队列与分配 | 事件幂等、持久化任务、账号选择、等待恢复和结果状态 |
| 存储与运维 | 数据迁移、事务、备份恢复、日志和服务生命周期 |

前端按概览、账号、绑定、过滤、记录、设置拆分；后端避免继续将接口、路由策略、连接管理和发送状态集中在一个文件中。模块划分是目标，不强制机械套用目录模板。

### 6.2 数据模型与迁移

- 监测绑定、私信接收绑定、文案、权重、事件、发送任务和联系记录明确分工。
- 每类群组配置有唯一事实来源；移除重复保存、可能互相矛盾的监测范围。
- 清理旧 `account_b` 必填列及监测独立运行时的占位兼容方式，使用真实可表达业务关系的数据模型。
- 任务应能够追溯事件、来源群 ID、转发目标 ID、账号、配置版本或必要快照，避免编辑现行配置后丢失历史含义。
- 迁移需覆盖旧文案、群绑定、未完成任务、去重记录及加密会话，不能通过删除数据库完成升级。
- 监测与私信的状态拆分应先明确暂停与恢复语义，再迁移，不由重构顺便改变发送范围。

### 6.3 并发与可靠性

- 消息接收不等待实际发送完成；排队与重复事件判断持久化。
- 不同账号的网络等待相互隔离；同一账号保持受控、有序执行。
- 后台长操作不阻塞网页登录、配置查询和状态反馈。
- 关键竞争场景包括重复接收、同时解绑与发送、修改文案与分配、断线与恢复、崩溃与结果提交。
- 先保持适合当前资源条件的单实例部署；未经容量证据不引入分布式架构。多实例方案必须先解决会话独占、分配一致性和队列锁。

## 7. 交互与性能目标

- 表单输入、焦点和滚动位置不因后台刷新丢失；关闭未保存表单时有明确处理方式。
- 保存、请求验证码、登录、同步等操作有进行中、成功和失败反馈；防止重复提交。
- 保存成功意味着后端已确认持久化；失败时保留输入，不能显示虚假成功状态。
- 群 ID 与目标关系始终可见，长 ID、长文案和多条绑定不能造成手机页面横向溢出。
- 区分已填写 ID、已验证可访问、无读取权限、无发送权限、账号登录失效和连接异常。
- 区分服务进程在线、账号连接在线及业务规则启用，避免“已部署”被误解为“已开始发送”。
- 记录应支持按状态、用户及必要的绑定/账号信息定位问题；列表分页，避免一次读取所有历史数据。
- 响应耗时、吞吐量、内存和可支持账号/群数量需通过基准测试确定。没有测量数据前，不承诺具体容量和零延迟。
- 单账号慢请求、平台等待或断网时，其他账号及页面操作应仍能推进；通过故障注入验证，而非只在空载截图中判断流畅。

## 8. 安全与运维目标

- 网页操作认证、请求校验、错误脱敏、会话和应用凭据保护保持有效。
- 配置文件、数据库、初始凭据和备份限制读取权限；备份数据库时同时保留对应加密配置。
- 不把用户名解析异常或正文其他提及当作更换收件人的理由。
- 日志包含可关联的账号、规则、任务与错误类别，避免默认输出全文聊天、凭据或账务信息。
- 服务具备健康检查、开机启动、异常退出处理、资源观察和可回退发布方式。
- 数据备份需要一致性检查与恢复演练；同机备份不等于异地容灾。
- 真实测试使用指定测试账号、群组与收件人；自动化及浏览器模拟不向真实用户发送消息。

## 9. 验收标准

以下为后续优化应覆盖的场景清单，不表示所有场景当前已通过。

| 编号 | 场景 | 通过条件 |
|---|---|---|
| A01 | 两类账号登录 | 三字段登录可用，两步验证可选；错误明确且不泄露凭据 |
| A02 | 直接绑定 ID | 未同步群名称也能保存来源/目标/接收 ID；非法类型和越界值被服务端拒绝 |
| A03 | 精准来源判断 | 同名不同 ID 的群、未绑定群不会触发该规则 |
| A04 | 精准目标转发 | 消息只发到该规则目标 ID；不同绑定互不串群 |
| A05 | 监测独立运行 | 没有 B 或私信文案时，A 的筛选转发仍可运行 |

## 10. 待确认事项

1. **监测与私信完全解耦后的暂停语义**：暂停 A 后，是否允许 B 继续处理已经转发或排队的消息；私信是否需要独立启停开关。
2. **可信来源范围**：是否始终仅接受本系统 A 的标准消息；若扩大到人工或外部系统转发，需要明确可信发送者配置。当前不扩大。
3. **文案最终归属**：按私信账号、接收群还是独立模板维护；旧任务文案如何迁移，当前优先级保持不变。
4. **再次联系策略**：永久去重是否改为可配置时间窗；未确认前不自动重置联系记录。
5. **离线补偿策略**：是否补读离线期间消息，以及补读范围、过期时间和重复识别方式。当前仅新消息。
6. **重叠监测绑定**：同一来源事件命中多条绑定时是否都转发，或按什么规则合并；不能在重构时隐式合并。
7. **容量与体验指标**：账号数、群数、消息速率、历史保留周期、持续测试时长及页面响应指标，需结合实际业务量确认。
8. **外网访问与容灾**：公网域名/HTTPS、多设备访问、异地备份与恢复目标另行规划，不由结构重构默认扩展。

后续补充需求按“已确认需求 / 当前基线 / 目标 / 待确认”更新相应章节，保持事实和计划分离。

## 11. 面向用户的工作台优化（2026-10-15）

已确认方向：群发、监测转发和 AI 分析分开使用，账号共用；分析群组不依赖关键词。以下为本轮实现范围：

- 工作台提供三个独立入口，系统设置只保留公共连接、运行和后台访问配置。
- 群发任务用于单轮文字通知：保存草稿、查看目标与内容、启动或定时、暂停、继续、取消，以及逐群结果。一个任务固定一个发送账号，最多 200 个目标。任务名称、文字、目标和时间保存后保持固定；修改内容需新建任务。
- 监测转发保留原有关键词、排除规则与私信接收流程；增加按账号搜索、选择已同步群组，仍支持高级手填 ID。
- AI 分析使用单独的来源群范围、规则、接收群或私人用户设置。当前为一个摘要计划，不是多计划列表。支持每日定时、按新增条数和仅手动；触发条数与每次最多分析条数分别配置。
- AI 模块内提供连接测试（仅合成测试文字）、预览（不发 Telegram 消息）、立即生成并推送、运行记录。手动生成使用已保存设置；预览和连接测试也会消耗服务商额度。
- AI 来源限定为所选监测账号在所选群中收集的新文本，关键词不影响收集；不回补历史。显示范围内收集总数，超过分析条数上限取最新消息。分析时间范围、定时时间按北京时间呈现。
- 群发与 AI 均复用账号连接、账号锁和 Telegram 等待状态，发送前检查运行状态及发送权限。暂停只停止后续发送；已经发起的请求可能交付。结果不确定时记为待核实，不自动重发。
- 服务总开关控制所有模块；群发任务、监测绑定及 AI 自动摘要分别启停。仅手动摘要模式不执行自动推送，来源消息仍在服务运行期间收集。

持久化：新增 `broadcast_tasks`、`broadcast_deliveries`、`ai_summary_runs` 三张表；启动时通过现有 `create_all` 重复安全地创建。旧账号、绑定、历史消息和密钥保持原存储。AI 旧配置没有 `trigger_count` 时沿用旧 `message_count` 作为触发阈值。回退代码可保留新增表，旧版本忽略这些表；回退后新群发队列不会继续执行，重新升级才可恢复。回退操作先暂停服务、保存当前数据并恢复旧代码，不以旧数据库覆盖升级后的业务数据。

## 12. 账号退出与删除绑定（2026-10-15）

- 退出 Telegram 账号只注销所选账号的服务器会话，不要求暂停服务，不改变其他账号连接或任务启用状态。此账号的绑定和未发送队列保留，重新登录后按原配置继续；退出前已发起的请求可能已交付。
- 注销期间串行处理该账号操作，先停止该账号重连，再撤销会话。网络失败保留待注销会话供重试，账号暂不自动连接，其他账号继续运行。网页管理账号退出只结束网页登录。
- 账号管理的每条监测绑定以及监测转发列表均提供「删除任务」。删除有确认，之后从可操作列表移除并取消该任务 pending/waiting 消息，保留已发送、发送中、待核实记录及去重依据；其他绑定不变。删除不是撤回已发送消息。
- 数据库新增可空 `relay_tasks.deleted_at`，迁移可重复执行，旧任务默认未删除。已删除任务保持 disabled 并禁止通过编辑或启用接口恢复。旧代码回退后这些绑定可能重新显示为暂停状态，勿重新启用；历史记录始终保留。

## 13. 私信图文编辑（2026-10-15）

- 入口为「账号管理 → 私信账号 → 接收群组与私信文案」。支持普通 Unicode 表情、加粗、斜体、下划线、文字超链接和一张静态图片，提供不发送消息的预览。个人账号发送文字链接，不提供机器人专用的消息底部按钮。
- 图片限制为 5 MB、2000 万像素以内的 JPG/PNG/静态 WebP，上传后修正方向、压缩为 JPEG 并去除元数据。纯文字上限 3500、图片说明上限 1024 个 UTF-16 单元，验证时预留用户名替换长度。图片素材总存储上限 100 MB；移除配图解除当前绑定引用，保留历史队列需要的素材。
- 文字格式通过服务端白名单校验，Telegram 发送使用明确的格式实体；旧纯文字仍按原样发送。已填写旧任务专属文案时继续优先使用该文案；清空后采用私信账号的图文设置。
- 新增 message_assets 表及 sender_bindings/relay_jobs.copy_options 字段。迁移可重复执行，旧行默认空选项（纯文字、无图），图片保存在本地数据库。队列快照保存格式和图片引用；修改文案或配图取消受影响的待发送私信，发送前仍复查权限和绑定。
- 图片与说明作为一条 Telegram 消息发送，上传或发送结果不确定时保留待核实状态，不盲目重复发送。
- 部署新增 Pillow 依赖。回退前暂停服务、备份当前数据库，并取消或隔离尚未发送的富文本/图片私信；旧代码忽略新选项，直接执行新队列会丢失格式或图片。保留新增表及列，不以旧数据库覆盖当前业务数据。

## 14. 监听诊断（2026-10-16）

- 管理员可通过受现有登录鉴权保护的 `/api/accounts/{id}/listener` 查看连接、更新循环存活状态，以及该账号最近 100 条接收/筛选阶段记录。
- 诊断仅存内存，服务重启后清空，只记录时间、群 ID、消息 ID、任务 ID 和处理阶段，不记录消息正文、用户名或凭据；不自动补发历史消息。
- 连接在线与消息接收正常分开判断。Telethon 更新循环状态是版本相关的诊断值，缺失时显示未知；单凭连接在线不能确认消息链路正常。

## 15. 新消息核对补偿（2026-10-16）

- Telegram 推送继续即时处理；另外每轮结束约 15 秒后核对已启用监测任务的来源群，以及私信账号已绑定且对应启用任务的接收群。复用在线账号连接和账号锁，不新建登录会话。
- 首次核对、新增/变更任务及重新连接时，从当前最新消息建立基线，不自动回放既有历史。基线后按消息 ID 从旧到新读取，每群每轮最多 100 条、每账号每轮最多 10 群，轮换核对避免较后的群长期得不到处理。
- 核对消息复用原有事件处理、过滤、身份检查和数据库事件唯一键；推送与核对同时得到同一消息只产生一个任务。暂停、解绑、删除后停止相应核对；发送结果不确定仍不自动重发。
- 请求超时保留游标，平台等待按账号等待，不换号规避；账号错误隔离。诊断中区分建立基线、核对完成、平台等待及错误类型，不含正文或凭据。
- 此机制改善推送缺失，不保证无遗漏：服务离线期间、建立基线之前及读取前已被删除的消息不回补。繁忙群或平台等待会增加延迟。无数据库结构变更，回退代码即恢复纯推送监听。

## 16. 频道采编（2026-10-22 新增需求与实现）

- 独立导航“频道采编”，使用现有已登录账号读取频道。来源可填公开频道链接、用户名或已加入私有频道的完整负数 ID；启用时验证是频道并记录最新消息位置。只采集启用后的新帖，重新启用重新建立起点；持续启用期间重启保留已提交的游标。
- 默认来源 `qt00`，排除词“七天”。排除词仅匹配正文和媒体说明，不匹配频道标题；广告依据可编辑的推广用语和明确广告标记筛选。规则不执行图片 OCR 或视频分析，隐晦广告需人工核对。只阅读有权限的频道，不自动加入频道。
- 每个来源独立设置账号、规则和可暂留空的发布频道 ID。保存设置暂停采集；已有草稿的来源及账号保留，更换时新建配置。已有草稿不会因修改规则自动重写或重新分类。
- 图片、视频、文件及相册以来源引用保存，相册在分页边界补齐；不保存整段视频副本。被过滤的帖子保留原因和查看入口。来源附件删除或变为不可读后，原附件发布可能失败；可移除附件、保留文字发布。
- 人工模式下，合格帖子先进入待编辑草稿，显示原文与编辑区。支持加粗、斜体、下划线、文字链接、表情、预览和原附件保留开关。人工模式的保存与发布分别操作；全自动模式见第 17 节。发布采用复制媒体和编辑后的正文，保留内部原帖追溯链接。
- 发布频道需单独设置且与来源不同，发送账号须有频道发布权限。确认发布后进入持久化队列，发送前重新检查账号、配置版本和目标。配置变更取消旧待发布队列，发送已开始的结果单独记录。
- 单条图文的平台等待可延后发送；相册异常可能部分成功，标为结果待核实而不自动重试。进程中断时发送中的记录转为待核实。重复采集由来源与帖子 / 相册标识去重，草稿编辑使用版本校验。
- 新增 `channel_feeds`、`channel_drafts` 两张独立表，由既有 `create_all` 执行可重复的增量建表，不修改旧表。回退旧程序会停止频道采编后台循环，新增表保留但不再读取；回退前备份并核对待发布 / 结果待核实记录。


## 17. 频道全自动排版与发布（2026-10-23）

- 用户已确认最终流程为“读取新帖 → 过滤七天与广告 → 自动排版 → 自动发布”，无需逐条人工确认。每条来源单独选择全自动或人工模式，发布目标仍单独填写且与来源不同。
- 新建配置的网页默认选全自动；迁移既有来源时数据库默认保持人工模式，不擅自让其他既有来源开始发送。用户明确要求的来源通过配置开启全自动。目标暂留空时继续采集并排版为草稿；填写目标并重新启用只处理后续新帖，旧草稿不自动补发。
- 全自动模式启用且有目标时验证账号发送开关及目标频道发布权限。采集游标、帖子去重、自动排版内容、目标和配置版本在同一事务提交，合格新帖直接排队，不调用人工确认接口。
- 模板采用“档案标题、来源发布日期、事件经过、涉及账号、原文明示的交易信息”。标题可自定义；后续按第 18 节去掉编号及发布页脚。只移动明确标记的字段，不把叙述中的多个金额推断成损失金额，不推断事件类型，不用 AI 改写事实；未识别的内容保留在正文。国籍及账号同步时间从明确的资料区移除。
- 筛选始终先于排版，不因格式变化绕过关键词规则。相册仍作为一组处理，保留图片、视频及文件。正文超过媒体说明限制时，附件先发，完整正文随后分段发送；纯文字超过单条限制也分段，保留格式实体并按 UTF-16 长度处理表情，不静默截断正文。
- 暂停来源或保存设置会将尚未发送的自动队列留回草稿；发送前及分段之间重新检查模式、版本、权限、目标和服务状态。已经送达的分段 ID 及时保存；部分成功、超时或不确定结果留为待核实，不自动整帖重试。Telegram 明确要求单条尚未发送的请求等待时，遵守等待并保留任务。
- 网页提供无发送的自动排版预览，已有未发布草稿可手动套用模板。模板预览及套用本身不创建发送任务。
- 增量新增 channel_feeds.auto_publish/template_title、channel_drafts.automatic/config_revision，迁移可重复执行并保留原游标、状态、草稿和账号凭据。回退前暂停来源与全局服务，取消或隔离待发布自动队列及长文队列，保留待核实记录及备份；旧代码忽略新字段，直接执行新队列不能保留自动模式与长文语义。


## 18. 频道模板风格与文字格式（2026-10-23）

- 自动生成的标题去掉 `#编号`，底部去掉分隔线、附件保留提示和“查看原始信息”链接；后台继续保留原帖追溯入口。长图文先发无说明的附件，再发完整正文。正文中原有的证据链接保留。
- 每个来源新增表情风格：警示、醒目、简洁无表情；事件正文可选择普通、加粗、斜体、下划线、删除线、引用、等宽、剧透。账号及交易字段保留原有清晰分组，默认警示风格、普通正文。
- 自动采集、手动套用模板和无发送预览共用上述设置。设置保存沿用暂停来源、取消旧排队任务的行为，重新启用后用于新帖。旧草稿和已发布消息不批量重写；预览不保存、不排队、不发送。
- 草稿编辑器支持上述文字格式、文字链接、插入表情、插入日期文字及选中文字清除格式。日期按用户输入显示为静态文字，不伪装为 Telegram 原生交互日期实体。剧透预览可点击或键盘切换显示。
- 频道使用独立的格式白名单及 Telegram 实体解析，支持引用、剧透及 UTF-16 表情偏移；私信格式处理不变。等宽正文独立使用，服务端拒绝与其他格式的非法嵌套。
