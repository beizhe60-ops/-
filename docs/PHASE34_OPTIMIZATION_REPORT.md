# PHASE 3–4 优化与生命周期回归

2026-09-23。本轮完成前端请求管理、状态接口批量读取，并补资源生命周期测试。未部署；运行时调度、队列状态机、权重、去重、登录、Session、Schema 和现有业务规则均未修改。

## 前端请求管理

- 状态请求共用一个在途请求槽，慢轮询未结束时跳过后续 tick；仍保持 15 秒刷新间隔，隐藏页面和打开弹窗时不发起轮询。
- 保存或操作后的主动加载使旧状态响应失效；等待旧读取结束后发起新的读取，不把保存前的快照当作最新结果。没有跨请求配置缓存。
- 页面渲染按请求版本校验，迟到的页面内容及旧请求错误不会覆盖更新的操作结果。
- GET 请求设 30 秒超时，覆盖获取响应与读取响应体；成功、失败或超时都会清理对应定时器。超时保留现有页面，释放 pending，允许用户重试。
- 不给 POST/PUT/DELETE 添加超时或自动重试，以免把“浏览器取消”当作“服务器撤销”。慢写入仍保留 pending 状态。
- 后台轮询失败不再静默吞掉：每段连续故障提示一次，成功读取后恢复可提示状态，避免每 15 秒重复打扰。
- “刷新记录”只重新读取记录；全局服务状态仍由原有状态轮询更新，取消该按钮额外的状态查询。API 字段及记录筛选规则保持不变。

## 后端状态接口

账号完整具备角色资料时，一次读取 profiles、bindings、weights，在本次请求内复用映射，保持原账号排序、字段、默认权重、空绑定、凭据脱敏和在线状态计算。

若发现任何账号缺少 profile，则回到原逐账号 get_profile 路径，保留旧迁移触发顺序及副作用，不借查询优化重写迁移。没有新增索引、事务拆分、全局缓存或第三方依赖。

## 生命周期：补测试，保留实现

新增 tests/test_runtime_lifecycle.py，验证：

1. 两账号配置修改并 reload 十次仍只有两个客户端，每客户端一个 handler。
2. 停用账号断开对应客户端，重复 stop 不重复断开已移除对象。
3. connect/get_dialogs 失败时清理客户端并记录 connection_error。
4. 初始化被取消时断开客户端，不留下已注册 worker。
5. 重复 start 不产生第二主循环，stop 等待任务结束；重启创建新的循环。

这证明上述模拟场景，不证明真实 Telethon 的所有内部引用或长期网络异常均无泄漏。未修改账户锁集合和 Session 生命周期。

## 复跑方式

在 telegram-ops 目录使用已有 Python 环境运行 pytest。浏览器测试使用已安装 Playwright 与 Chrome：

```sh
PLAYWRIGHT_MODULE=/path/to/playwright node tests/browser/phase2.cjs
PLAYWRIGHT_MODULE=/path/to/playwright node tests/browser/phase3.cjs
```

共享的 helpers.cjs 仅启动本地临时静态服务及虚构夹具，退出时关闭。无需生产账号，不增加应用依赖。
