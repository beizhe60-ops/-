# Telegram Ops 阶段性架构审计

日期：2026-09-22。审计版本：`5085207` 工作区；应用代码最近提交 `c655fa1`。这是审计与未来计划，不是重构完成报告。

## 1. 范围与验证

完整阅读根目录 `AGENTS.md`、`docs/ARCHITECTURE_REQUIREMENTS.md`，以及 `telegram-ops/` 下全部应用模块、静态页面/样式/脚本、模板、辅助脚本、迁移文件与测试；检查依赖和启动配置。下文源码路径均相对 `telegram-ops/`。

本轮仅新增本报告。未修改业务代码、测试、数据库 Schema、legacy 字段、account_b、队列状态机、权重、去重、登录/Session 或 Monitor/DM 规则；未连接或修改生产服务器。已有两份需求/规则文档保持不变。

验证：在项目虚拟环境中执行 `python -m pytest -q`，结果 **41 passed，554 warnings，1.71s**。测试使用临时数据库及模拟客户端。警告主要为 `datetime.utcnow()` 和 Starlette/AnyIO 的弃用提示，不代表本轮出现业务失败。未进行真实 Telegram 联调、浏览器交互验收、负载测试或进程崩溃实验；未测量覆盖率百分比。

结论分级：

- **已确认结构事实**：直接来自源码、导入图及现有测试。
- **静态推断风险**：存在可达条件和代码依据，但本轮未用新实验复现。
- **待定业务语义**：需求尚未明确，不作为可以直接修复的 bug。

## 2. 当前结构及主要调用链

```text
console.html + console.js
  → console_api（校验、配置写入、查询、登录操作）
  → RelayEngine 单例
      ├─ 账号连接、身份缓存、后台循环
      ├─ Monitor：来源 ID + 过滤 → relay 入队
      ├─ DM：接收 ID + 可信 A + 标准文本 → dm 入队
      ├─ Assignment：候选过滤 + 持久化平滑加权轮询
      └─ Queue：领取候选 → 身份/权限/去重校验 → Telegram 发送 → 结果保存

main 同时暴露旧 HTML 管理路由
console_api/main → workers 中仍在使用的登录及群同步函数
数据库 → Account / Profile / Binding / Task / Job / Receipt / ConsoleState
```

旧 `WorkerManager` 与 `Rule/SendQueue` 系统仍保留，但当前 `main` 使用的是 `relay_engine.manager`。不能把“有两套代码”说成“两套引擎正在同时发送”。旧管理路由仍可访问且受后台认证约束，不能把它们当成完全不可达的死代码。

## 3. 最需要控制的技术债

| 优先级 | 位置 | 已确认事实与影响 | 本阶段处理 |
|---|---|---|---|
| P1 | `app/relay_engine.py:28`、`:396`；`app/console_api.py:123`、`:402` | 同一类管理五个业务域；队列发送、连接重载和部分配置修改共用全局锁，锁内等待网络 | 暂停增加跨域职责；补慢请求/配置竞争特征测试。拆锁、并发化延期 |
| P1 | `app/relay_engine.py:396`、`:416` | 队列按 ID 取前 10 条；账号不可用、发送关闭或 worker 不在线时直接返回，任务仍可能保持到期待发 | **静态风险**：前 10 条均长期不可执行时，后续可执行任务可能持续取不到。先建立复现测试；调度修复会改变执行行为，另行报告 |
| P1 | `app/main.py:145`、`:196`、`:223`；`app/console_api.py:322`、`:359`、`:579` | 新旧管理入口均能修改共享账号/运行状态。旧登录入口没有新 API 的账号锁；旧启停不写持久化运行开关；旧新增账号不直接创建新资料和接收绑定 | 补入口一致性测试和调用清单。不能直接删除旧接口或顺手改启停语义 |
| P1 | `app/relay_engine.py:154`、`:220` | DM 仍遍历启用的 Monitor 任务，并依赖 A 的内存身份。来源记录按任务、相同文本和最近记录匹配，不按已发送消息 ID 关联 | 锁定当前暂停/可信来源语义；**静态风险**：同文事件可能关联到不同来源快照。补同文、群名含连字符和来源缺失测试 |
| P1 | `app/relay_engine.py:489`、`:497` | 联系记录在实际发送之前提交；失败、取消或结果不确定时记录不会自动释放 | 这是当前去重语义，不能当清理冗余直接删除。补跨任务和失败后再次入队测试，先明确“预占”与“成功联系”的含义 |
| P1 | `app/console_api.py:263`、`app/account_settings.py:41` | 来源范围在 Profile 与 Task 各存一份；读取账号资料可以触发全局资料迁移并 flush | 防止再增加第三份来源；补历史数据和只读接口副作用测试。统一事实来源涉及兼容，延期 |
| P2 | `app/database.py:35`、迁移目录 | 启动 create_all + 运行时资料迁移并存；Alembic 仅导入旧 models，初始迁移使用动态 metadata | 新数据库通过不同入口初始化可能得到不同表集合；本轮未运行迁移。先做临时库基线，正式迁移体系单独规划 |
| P2 | `app/console_api.py:279`、`static/console.js:692` | 全量 state 查询、账号序列化逐项查询及前端 15 秒轮询；引擎每条消息查询全部启用任务；异步流程中使用同步数据库 | 存在扩容成本，尚无实测容量结论。先测查询次数、事件循环延迟及耗时，再决定缓存/分页/索引方案 |

其他应记录的边界：

- 新 API 删除不再联系记录会删除整条 `UserGuard`；旧入口可以分别保存 blacklist/unsubscribe。取消某一种标记是否应保留另一种，必须先确认语义，不能借整理接口改变。
- `enqueue` 捕获所有 `IntegrityError` 并视作重复事件忽略，可能掩盖其他约束错误。先补错误分类测试；增加脱敏诊断可以独立做，但改变返回/重试行为不是低风险整理。
- 配置开关、任务取消等入口与持锁发送的同步方式不完全一致。代码有发送前复核，但不能据此保证外部请求已经开始后仍可撤回；需要按真实 await 边界补测试。
- 健康检查的 `ok` 和 worker ID 列表不能充分证明队列循环、数据库和 Telegram 链路健康；监控语义的扩展应单独定义。

## 4. 高耦合和过大职责模块

行数仅辅助定位，不能作为机械拆分标准。

| 文件 | 行数 | 职责判断 | 风险 |
|---|---:|---|---|
| `app/relay_engine.py` | 551 | 生命周期、事件处理、分配、队列、身份验证、去重和异常落库；send_job 133 行、on_message 98 行 | 最高；不能只按函数长度搬文件 |
| `app/console_api.py` | 645 | 输入模型、业务校验、配置变更语义、数据拼装、认证设置、网络生命周期；直接访问 manager 内部锁/worker | 高；薄路由化也必须先固定事务与锁边界 |
| `app/workers.py` | 522 | 历史完整引擎与当前仍使用的登录、Session、群同步共存 | 高；不能整文件标记废弃或删除 |
| `app/main.py` | 362 | 应用启动、认证中间件、新 API 挂载及旧界面写接口 | 高；职责多于入口装配 |
| `static/console.js` | 701 | 页面生成、表单、请求、登录步骤、状态、轮询和事件绑定；长模板字符串增加维护难度 | 中；纯展示/helper 可小步拆，登录和提交时序暂不动 |
| `static/console.css` | 1094 | 当前仍是统一控制台样式，包含组件与响应式规则 | 低至中；长不等于职责失控，拆分须保持加载顺序与级联 |
| `app/rules.py` | 216 | 旧规则匹配、限额、模板、线索与队列 | 兼容风险；与新 relay_logic 名称近似但语义不同 |

前端现状纠正：轮询在弹窗打开或页面隐藏时跳过，只自动重绘概览；不能宣称所有表单每 15 秒都会丢失输入。缺口是未有可重复的浏览器测试证明保存失败、登录步骤、刷新和连续操作都保持状态。

## 5. 重复代码、重复状态和配置分散

### 5.1 状态归属清单

| 状态/配置 | 当前保存位置 | 判断 |
|---|---|---|
| 来源群集合 | AccountProfile.monitor_chat_ids / RelayTask.source_chats | 独立持久化且引擎同时检查；存在漂移风险。任务编辑登记为并集，未必缩减旧范围 |
| B 关系 | legacy account_b / SenderBinding / role | 新旧表达共存，account_b 有 A 占位兼容。明确冻结，不清理 |
| 文案 | RelayTask.template / SenderBinding.template / RelayJob.text | 前两者存在优先级；Job 是发送快照，应保留，不是简单重复 |
| 运行状态 | RelayEngine.running / ConsoleState.running / 环境自动启动配置 | 运行事实、持久化意图和默认值不同；统一入口语义，不简单合并字段 |
| 账号状态 | Account.status / worker.client / identities / flood_wait_until / 登录标记 | 分别描述持久化状态、连接、身份和等待；需要生命周期边界，不能只保留一个布尔值 |
| API 凭据 | 全局应用设置 / 账号加密凭据 | 当前是有意的新增账号快照规则；不应随全局更新覆盖旧账号 |
| 分配状态 | SenderWeight / ConsoleState sender_rotation / RelayJob.account_id | 权重、轮询进度和分配结果不同；事务一致性比合并字段重要 |

### 5.2 可疑重复代码

- 新旧路由中账号、登录、启停、名单处理相似，但校验、锁与持久化不同：**不能直接去重**。
- workers 旧事件处理器有重复的事件转换/数据库查找；默认路径并未使用旧引擎，低收益，不优先碰。
- 密码散列脚本与认证模块有相同算法，可在测试保护下提取纯函数；新工具模块不能反向引入 Web/数据库依赖。
- Python/API 与 JavaScript 的 ID、权重、长度检查存在重复，前后端独立校验是必要防线。可固定一套边界测试，不能取消服务端检查。
- 旧 `split_keywords` 与新 `words` 的大小写处理不同；旧模板与当前模板语义不同；不得按名字合并。
- 账号序列化多次查同一权重等局部重复读取可考虑优化，但先锁定输出与查询基线，不扩展为查询层重写。

### 5.3 constants / config / error handling

- `config.py` 的轮询、健康检查、限额等部分设置服务于旧引擎；新引擎存在 2 秒循环、每 10 次循环重载等直接值。把新引擎改为读取旧配置可能改变生产行为，不属于只集中常量。
- 群数 200、权重 1–1000、文案 3500、消息长度、列表分页 50 等分布在 API/逻辑/前端。可提取保留原值和原导入时机的具名常量；不得在同一改动中“统一”不同业务限制。
- `ConsoleState` 混存应用配置、管理员密码散列、运行意图、登录标记和 JSON 轮询状态。先定义键名、数据形状和所有者文档；更换存储结构延期。
- 旧 `enums.py` 与当前引擎字符串状态并不完全相同，例如 flood_wait/waiting。可增加静态类型，不能替换成带不同转换行为的新运行时枚举。
- 登录错误有单独映射；引擎保存异常类和文本；旧 worker 有 print；前端轮询 catch 为空；过滤分支部分静默跳过。先规定脱敏字段（account_id/task_id/job_id、阶段、错误类别）及日志级别，不改变错误到状态的映射。
- `datetime.utcnow()` 替换成 aware 时间会影响比较、数据库值和序列化，虽然是弃用警告，也不能全局自动替换。

## 6. 循环依赖检查

通过 AST 检查 `app` 内 `import` / `from ... import ...`，区分模块顶层与函数内导入：

- **未发现模块顶层的静态导入环。**
- 包含函数内导入时存在 `database → models → database`、`database → relay_models → database`，以及 `database → account_settings → models/relay_models → database` 等环。
- 环来自 `init_db` 注册模型、运行资料迁移，模型再引用 Base。当前依靠延迟导入打断初始化，没有证据表明它目前触发 ImportError。
- 真正问题是数据库基础定义、建表和业务迁移相互依赖，容易让脚本/测试不同的导入顺序得到不同 metadata。未来移到显式应用装配阶段；现在先补启动与独立脚本导入测试。

这不是第三方库完整动态依赖审计，未检查运行时动态 import 的所有可能路径。

## 7. 缺失的 Characterization Tests

目标是记录当前可观察行为，尤其是不理想但现存的行为。不能把未来目标写成当前必须通过的测试，再借修红灯改变业务规则。对未确定的行为先做隔离探针、记录结果，再决定是否固定成回归基线。

| 优先级/域 | 应补场景 | 必须观察的结果 |
|---|---|---|
| P0 Queue | 前 10 条账号离线/关闭发送，第 11 条可执行；连续多个 tick | 实际领取集合、状态是否停留、后续是否饥饿；暂不修改调度 |
| P0 Queue | get_entity/send_message/connect 慢请求，同时保存配置、停止服务 | 锁持有范围、等待时间、取消状态；使用可控 Future，避免睡眠型不稳定测试 |
| P0 DM/Dedup | 不同任务、不同 B 联系同一用户；发送永久失败/取消/unknown 后重新入队 | 全局唯一联系记录、最终状态、实际发送次数；保留当前预占语义 |
| P0 Assignment | 两个不同 B 同时接收同一事件；DB 提交失败；重复事件重放 | 仅一次有效任务和进度推进，失败事务是否回滚；分别记录两个客户端调用 |
| P0 Lifecycle | 重复登录/同步/退出/重载并发，connect 或 disconnect 失败，授权过期 | 客户端拥有者、连接清理、账号状态、临时 Session/2FA 标记和锁释放 |
| P0 Recovery | 独立子进程发送前后中断、发送返回后 DB 提交失败 | sending/unknown 恢复、receipt 保留、绝不盲目重发；临时库+模拟客户端 |
| P1 Monitor/DM | 多任务重叠来源/目标，暂停 A 后 B 收到消息；不可信发送者 | 当前逐任务和启停耦合行为；不擅自合并路由或解耦 |
| P1 Correlation | 连字符群名、相同格式文本的不同来源、找不到源记录、用户名变化 | 解析回退、来源选取、身份核对与最终收件人 |
| P1 Templates | 旧任务文案与分配账号文案刻意不同，旧文案清空，空模板候选 | 文案优先级、任务快照、轮询进度是否受空模板影响 |
| P1 Assignment | 候选增减、修改权重、同权重并列、无候选、平台等待、重启 | 顺序/重置/回退规则与旧任务账号不变；不只验证长期比例 |
| P1 API/Legacy | 旧/新登录与启停入口、Guard 两种标志、缺 Profile 账号查询 | 响应、持久化状态、锁与资料创建差异；避免意外强化旧入口 |
| P1 Login | 正常验证码、重发/过期/错误码、直接带错 2FA、第二次补密码 | 错误映射、步骤保持、临时会话清理及秘密不回显 |
| P1 Init | 重复 init、空库 Alembic 与应用启动、已清空绑定、部分历史资料 | 表集合/数据变化与幂等；仅临时库，不运行生产 downgrade |
| P1 UI | 获取验证码→登录→绑定；失败保留输入、重复点击、打开弹窗后轮询、窄屏长 ID | 真正执行 JS 的浏览器回归；HTTP 200 不能替代 |
| P2 Performance | 增加账号/任务/历史量；单账号慢网 | 查询次数、p95 页面耗时、事件循环延迟、队列年龄及内存基线 |

现有测试的有效边界：

- 已覆盖主要转发/接收、绑定、过滤、权重比例及持久化、FloodWait、用户名变化、unknown、配置变化等，不能说“没有测试”。
- `test_global_dedup` 使用同一任务下的两条工作，未完整证明跨任务场景。
- 加权测试复用同一个模拟客户端对象，能验证数据库分配比例，不能充分证明消息实际交给了不同客户端。
- 已有重复事件接收测试不等于真正并发竞争测试。
- restart 测试在同一测试进程里启动引擎，不等于 OS 进程中断/持久化故障恢复。
- `test_pages` 主要证明接口返回页面，不执行浏览器 JS；没有进入当前 pytest 基线的浏览器验收不能被计入这 41 项。

## 8. 现在可做的 LOW RISK 工作

以下是可独立提交的候选，不是本轮已执行。一次只做一种，先有行为基线，测试若要求业务改动则停止并报告。

1. **优先补上述特征测试和独立客户端 mock**：固定数据库、事件及时间输入；隔离引擎单例、缓存和后台任务；不得触达真实账号。
2. **纯工具整理**：重复密码散列等无副作用工具；保留算法、参数、返回值及错误类型。不要合并新旧过滤器/模板器。
3. **常量命名与配置来源注释**：原值原路径语义不变；标注 legacy-only 设置。将运行时配置真正接入现有引擎另案评估。
4. **静态类型补充**：ParsedEvent、序列化返回结构、模拟客户端协议、状态 Literal；不改变 Pydantic 校验/coercion 或 SQLAlchemy 列定义。
5. **纯前端展示/helper 小拆分**：转义、时间/状态显示、静态卡片生成。保持 script 顺序、事件绑定、DOM 和登录步骤；需浏览器回归后才可交付。
6. **脱敏 logging 统一**：不改异常分支、状态和重试；不输出正文、API Hash、验证码或 Session；先验证日志格式和敏感字段。

本阶段避免“utils 大杂烩”、仅为减行数拆 service，以及为了共享五行代码引入新的全局依赖。新增功能尽量复用现有稳定边界，跨域动作先补测试再加，防止继续扩大引擎与路由职责。

## 9. HIGH RISK：功能稳定后再做

- Monitor/DM 完全独立启停、可信来源扩大、历史补偿、重叠规则合并。
- account_b 清理、Profile/Task 单一来源、文案归属变化、legacy 表/字段/接口移除。
- 队列公平性修复、领取方式/锁/事务边界、并行发送、多 worker、重试或状态机变化。
- 权重算法、候选变化处理、无候选回退、轮询进度保存时机变化。
- 联系记录释放/过期、去重窗口、发送前预占改为发送后确认。
- 登录、2FA、Session 与连接拥有者重构，重连和账号故障策略变化。
- Schema/索引/版本化迁移、时间类型语义调整、同步数据库换异步数据库。
- 微服务、外部队列或分布式部署。没有容量证据时不引入。

即使以“抽类”“接口封装”命名，只要触碰以上执行顺序、锁或事务，就不归 LOW RISK。确认是缺陷也不意味着本轮获准修复；单独说明影响、最小方案、回归测试和回退方式。

## 10. 推荐正式重构触发条件

同时具备以下条件后，再按域启动，不要求全项目一次重构：

1. **规则稳定**：相关域连续两个功能迭代没有核心语义改动；需求第 10 节中涉及该域的暂停、文案、可信来源、重叠路由及去重决策已记录。两迭代是建议门槛，不是已确认日程。
2. **行为可证明**：相关 P0 特征测试、身份/绑定负例及重启/失败场景可重复通过；已知异常行为单独列明，不以重构名义悄悄修复。
3. **有实际收益证据**：功能修改反复跨多个域，或基准显示队列等待/网页延迟/账号故障影响超过约定目标。先与实际规模约定指标，不能凭行数决定。
4. **能恢复**：临时库迁移与备份恢复演练通过；部署与旧机器人隔离；回退步骤与凭据/数据兼容策略明确。
5. **能小步交付**：确定一个域、保持兼容的边界和可审阅的小提交；行为调整和结构调整分开，避免同时重写五个域。

## 11. Future Refactor Roadmap

| 阶段 | 范围与交付 | 出口标准 |
|---|---|---|
| 0：现在 | 特征测试、状态/配置归属图、调用清单、故障与性能基线 | 关键旧行为有证据，已知风险和待定规则分开；不修改业务 |
| 1：开发期可选 | 纯工具、具名常量、静态类型、脱敏日志、纯 UI helper | 输出/异常/请求/状态均保持；单元与必要浏览器回归通过 |
| 2：稳定后 Account Lifecycle | 逐步明确登录、临时 Session、已登录 Session、连接/身份缓存和退出的唯一管理入口；先保持原时序 | 正常/2FA/过期/失败/并发/取消测试一致。拆锁与重连策略必须作为单独行为变更 |
| 3：稳定后 Monitor / DM | 先抽取事件输入、路由/过滤判断和标准消息解析边界；维持可信 A、task.enabled、模板优先级及来源选择 | 旧新实现对同一模拟事件输出一致。完全独立启停及来源关联规则另案批准 |
| 4：稳定后 Assignment | 候选构建、平滑加权计算、轮询状态读写职责分离；原集合排序、算法、回退与事务保持 | 多 B 并发、重复/失败回滚、权重变更/重启，分配与进度结果一致 |
| 5：稳定后 Queue | 生命周期/策略边界稳定后拆编排、执行与结果记录；先保持单实例与原状态迁移 | 崩溃窗口、等待、取消、receipt 及发送次数回归通过。公平性/并发/锁优化独立评审 |
| 6：独立数据与兼容治理 | 依据已定规则设计版本化迁移、唯一事实来源、legacy/account_b 退出计划 | 旧库升级、重复执行、待发送任务和加密会话保留、恢复验证全部通过后实施 |

各阶段不必等所有域稳定，但不得跨越其依赖和冻结约束。影子对照仅在模拟/回放环境比较结果，不启动两套真实发送路径。持续功能开发期间，用小范围特征测试和纯工具整理控制新增债务；达到条件后再执行正式结构重构。
